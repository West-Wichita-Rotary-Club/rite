## Proposed Change

### Principle: XI. Test Coverage and CI Are Established (enforced)

> `docs/js` carries a test suite (state, i18n, content, account, router) run via Node's built-in
> test runner, plus a lint script; both run in CI (`.github/workflows/ci.yml`) on every pull
> request, and the `test` job is a required status check on `main`. `src/Rite.Api` and
> `src/Rite.Web` each carry their own test suites (`dotnet test`, `npm test`), run in CI the same
> way. New production code must extend this coverage, not bypass it; a surface shipped without
> matching tests is incomplete, not merely untested.

**Rationale**: The gap this principle named was closed by ps-005 (2026-11-16) and has stayed
closed since (`src/Rite.Api`'s and `src/Rite.Web`'s own test suites, added by ps-006/ps-007 and
extended through ps-015, both run in CI the same way). Leaving the old title and `adopting`
status in place misdescribes the project's actual, now-enforced practice to anyone reading the
constitution — exactly the kind of drift this command exists to catch.

**MUST Requirements:**

- Every CI-gated project (`docs/js`, `src/Rite.Api`, `src/Rite.Web`) keeps a passing test suite
  as a required status check on `main`.
- New production code adds or extends tests in the same change, not as a deferred follow-up.

**SHOULD Recommendations:**

- Prefer testing a new pure helper or component directly over only exercising it indirectly
  through a larger integration test, matching this repo's existing pattern.
