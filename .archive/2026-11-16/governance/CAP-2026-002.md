## Proposed Change

### Principle: X. Hosting Direction (adopting)

> Plan for hosting on an existing VM, with services reachable under `makeboldspark.com`
> subdomains — the API at `rite.makeboldspark.com`. Media (high-resolution photos, videos,
> transcripts, and other archive assets) is stored on that VM's filesystem, with SQLite-managed
> metadata, unless and until a dedicated object-storage need is identified.

**Rationale**: The project now has an existing VM to deploy to, and a concrete hostname for the
API (`rite.makeboldspark.com`), decided directly by the developer on 2026-11-16. Azure was always
an `adopting`-status aspiration with no provisioned resource; nothing has shipped against it. This
amendment replaces that aspiration with the actual target so ps-007 and future deployment PSs are
specified against real infrastructure instead of a plan that was never acted on.

**MUST Requirements:**

- Production services (API, and the React site once ps-007 ships) deploy to the existing VM.
- The API is reachable at `rite.makeboldspark.com`.

**SHOULD Recommendations:**

- Prefer VM-local storage for archive media unless a specific need (scale, CDN, durability)
  justifies introducing object storage later; re-open this principle explicitly if so, rather than
  silently reintroducing a cloud-storage dependency.

With:

> **Stack:** ASP.NET Core MVC/Web API, React (standalone, calling the API), SQLite, existing VM
> hosting (`makeboldspark.com` subdomains).

### Additional Constraints: Current shipped surface line

With:

> no backend, database, or hosting is live yet.
