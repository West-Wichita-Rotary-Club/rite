## Deployment & Handoff Notes

### Deployment Notes

- This diff adds `AlumniClaims` and `Memories` tables via `OnModelCreating`, which `EnsureCreatedAsync` will not add to an already-existing SQLite file — the same pre-existing gap ps-009's and ps-010's columns had, and still moot today since production (ps-008) has not been deployed.
- The local dev media root (`src/Rite.Api/media/`) is now gitignored, matching `rite.db`'s existing treatment.

### Observations

- `DecodeJpegDataUrl` validates the `data:image/jpeg;base64,` envelope and a size cap, but not that the decoded bytes are actually a JPEG (no magic-byte/SOI check). A client could upload arbitrary bytes labeled as a JPEG, and `GetMemoryPhotoAsync` would serve them back with `Content-Type: image/jpeg`. Today this is unreachable as an attack: a photo is only ever served back to the uploading account itself (confirmed by the ownership check), so there is no second party to target. This becomes worth hardening once ps-018's review/approve workflow gives a coordinator or editor a reason to open another account's memory photos — flagging it now so that PS doesn't have to rediscover it. Not a finding against this PR: no consequence is reachable in its own scope.
- `CreateMemoryAsync`'s per-account cap check (`CountAsync >= 10`) is read-then-write with no transaction or unique constraint behind it, so two concurrent submits from the same account could both pass the check and produce 11 memories instead of 10. This mirrors PR #19's M-01 in shape but not materiality: M-01 broke a *documented, tested* 409 contract via a real unique-index race; this is a soft UX limit with no security or data-integrity consequence, self-inflicted by the same account that would benefit from the race, and trivially correctable (delete one). Recorded for completeness, not as a finding — the bar PR #19 set for a blocking race was a violated hard guarantee, which this isn't.
